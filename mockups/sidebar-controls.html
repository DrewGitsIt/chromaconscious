what is actually wrong today

Not "the icons are small" on its own. Four separate things stack up in the .sec-act slot, and each makes the next one worse:

  • 22px pills, 11px glyphs, --ink-faint ink. .mini is height:22px and its resting colour is #6a6e7a on #17181c — about 2.3:1. It is legible only on hover, when it finally gets a border and --ink-muted. A control that is invisible until you touch it cannot be discovered by looking.
  • Two of the five carry no word at all. start-over is a lone palette glyph; back-one-riff is a lone RotateCcw — the same glyph reset uses, two pills away, meaning something else. Reset says "reset"; back says nothing.
  • The cluster changes shape underneath the pointer. reset and back are conditionally rendered, not disabled, so riff moves horizontally the moment you press it (back appears to its right) and again when you clear placements. Press riff twice quickly and the second click can land on the button that just appeared.
  • It does not fit. Measured live under column 1: the header can give the tools about 213px, and the shipped cluster wants 233px mid-session and 242px with mono engaged. .sec-rule is already collapsed to its 8px minimum in both, so the row is over budget with nothing left to give.

the three directions, and what each is buying

directionoptimisescosts
1 · spell it out legibility and stability — every verb has a word, nothing is ever added or removed, so no target ever moves. ~35px of sidebar height, and five equal pills means nothing reads as the primary action.
2 · one object says which controls belong together: back and riff become one segmented walk widget, so "3" reads as a position on a path rather than a badge. reset and start-over go behind an overflow, and that overflow is itself an icon-only button — the very thing being fixed, kept on purpose in one place.
3 · one big verb the action pressed twenty times a session gets a 32px full-width target and room to explain itself when disabled. another full-width element under the board, and three verbs one click deeper.

recommendation

Direction 3, with direction 2's walk group inside it.

riff is the only control here that gets pressed repeatedly, and the only one whose disabled state needs a sentence rather than a tooltip — both of those argue for width, and width is exactly what the header slot cannot give. Promote riff (with back welded to its right edge, the segmented idea from direction 2) to a full-width control under the board; drop mono, reset and start-over into one labelled palette ▾ menu, where they can carry full sentences and destructive wording. That leaves the section header holding one labelled button instead of five glyphs, which is the only version that still fits at 320px in every state.

The concession direction 3 has to make is that an engaged mono is a mode, and a mode hidden in a menu is a mode you forget you are in — so it surfaces as a small swatch chip beside the section label whenever it is on (visible in the mono on state). Direction 1 is the safe fallback if the extra full-width control is judged too heavy; it fixes legibility without moving anything.

accessibility, stated per direction

  • Every control gets a real accessible name. Today four of the five rely on title alone for their name — which works in most screen readers but is not a name, it is a tooltip, and it is not exposed to touch or to speech control at all. All three directions carry a visible word or an explicit aria-label, and title is demoted to the explanation ("walk the palette one hop; locked seats hold still").
  • 24px minimum hit target even where the glyph is 11–13px. Turn on the switch at the top: every button in the sheet is measured live and outlined by whether it clears 24×24. Today's .mini is 22px tall and the icon-only ones are ~27px wide, so they fail the height on every one. The directions run 26px (1), 24px + generous padding (2) and 32px (3).
  • Focus. .mini defines no :focus-visible rule anywhere — it inherits the UA ring, on a pill whose border is transparent. The directions use the same 2px --accent ring the board seats already define, so keyboard focus looks like the rest of the app.
  • Disabled vs aria-disabled. A real disabled button is removed from the tab order and its title is never announced, so "why can't I riff?" is unanswerable by keyboard. Directions 1 and 2 use aria-disabled="true" and keep the button focusable; direction 3 does not need the trick because the reason is written on the control.

the quiet-control problem (and what it means for the seat lock)

The seat padlock is out of scope, but it has the same disease as this cluster: it is opacity:0 until the seat is hovered, so a first-time user has no way to learn that locking exists. Direction 3 has a clean answer that does not touch .rb-lock at all — the primary control names the mechanic. When riff is a full-width button reading "riff — one hop · locked seats hold still", and it goes flat with "every seat is locked", the word locked is on screen at full size before the user has hovered anything. The padlock then only has to be findable, not explanatory. The cheapest complement is the one direction 1 already implies: on a board where nothing is locked yet, keep one padlock visible at rest rather than all six or none.

what the real CSS constrains harder than expected

  • 286px, not 320. .sidebar-shell is width:320px and .sb-body adds padding: 4px var(--pad-side) plus a thin scrollbar, so the content box measures 286px. The header spends the label ("colors" = 49px), two 8px gaps and the rule's 8px minimum before the tools get anything — a hard ceiling of 213px for the whole cluster. Every column reports its own number live, under the trade-off note.
  • An over-wide header does not spill, it scrolls. .sb-body is overflow-y:auto, which forces overflow-x to compute to auto too — so today's over-budget cluster buys a horizontal scrollbar across the whole sidebar body rather than a visible overhang. That is why the problem has been easy to miss: it shows up as the panel feeling slightly loose, not as a button hanging off the edge.
  • .sec-act is flex-shrink:0 and .sec-label is white-space:nowrap. Nothing in that row can give, so an over-wide cluster does not wrap or truncate — it pushes. Any direction that wants to live in the header must budget for the worst state (mono engaged + reset + start over + riff with a two-digit hop + back), not the empty one.
  • The mono pill's width is data-dependent. .mini.on renders the anchor role name — primary, warning, success — so engaging mono can widen the cluster by ~25px depending on which seat you picked. A swatch is a fixed 12–14px and removes that variance entirely, which is a second reason the user's "show the colour" instinct is right.
  • The riff hop count sits inside the button. {frame.seed > 0 ? frame.seed : ''} means the button silently grows a character at hop 1 and again at hop 10, shifting everything to its right. Any hop display should be a fixed-width slot.
  • The bench bar is already full width and still quiet. Its problem is not size, it is font-size:var(--fs-xs) (10px) in --ink-faint. All three directions apply the same one-line fix — 32px tall, 11px label, muted ink, count in a real badge — because it is not the axis these directions differ on.
  • A popover on the add row is clipped by two boxes. .sidebar-shell is overflow:hidden (deliberately — "the footer's frost must not bleed past the edge") and .sb-body is overflow-y:auto, which also clips. The shipped .picker-pop opens with top: calc(100% + 6px) from a control that sits at the bottom of its section, so it can only ever be scrolled into view, never shown in place. The + swatch here opens upward (bottom: calc(100% + 6px)) in the sidebar columns and downward in the isolated panels — click one of each to see the difference. A real implementation should flip on available space, or portal out of the shell.
  • The add row is two controls doing one job. .hexfield already embeds a 20px ColorSwatchPicker that opens its own popover, and then there is a separate Add button — so the swatch and the button both "add", by different routes, with different results. That is the real reason Add is the only control the user reads as working: it is the only one that is a word.

two bugs found while reproducing this

1 — the placeholder promises a syntax the field cannot accept.
ColorAddField.commit() does text.split(/[\s,]+/) before parsing, so oklch(0.7 0.12 250) — the example printed in the placeholder — is shredded into oklch(0.7, 0.12, 250) and every fragment fails parseColor. Same for rgb(91, 124, 250). Only comma-free, space-free tokens survive.
2 — invalid input is answered with silence.
addCandidates filters unparseable tokens and returns early when nothing survives: if (parsed.length === 0) return. Type junk, press Enter, and the field does not clear, nothing is added, nothing is said. The popover below fixes both — it tokenises at paren depth 0, and it says what it could not read.

what the popover does on invalid input

  • The field border turns --fail and the caption names the failure — "can't read #gg12 — try #e63946, rebeccapurple, oklch(70% .12 250)". It never silently drops a token.
  • Add is disabled, not destructive. Enter does nothing while the text is unreadable, and nothing is committed or cleared, so the typo is still there to fix.
  • The swatch holds the last valid colour. The picker does not flash to black or to white on a bad keystroke, because a picker that jumps while you type is a picker you stop trusting.
  • Partial input is partially valid: paste #e63946 nope #3fa06a and it offers "add 2 colors · 1 unreadable" with the bad token underlined, rather than an all-or-nothing refusal.
  • An already-present colour is not an error — it reads "already on the board" and Add stays available (it re-adds nothing), matching the existing has() dedup.
